# Gestion Cross — audit et mise à jour du 1er octobre 2026

## Complément du 2 octobre : courses mixtes

Les classements individuels regroupent désormais les élèves par **niveau et sexe**.
Une course commune peut ainsi produire « CP · filles », « CP · garçons »,
« CE1 · filles », etc., jusqu’à la terminale. Les classes A/B d’un même
niveau et du même sexe partagent leur classement. Les rangs repartent à 1
dans chaque catégorie, sans modifier l’ordre d’arrivée commun ni le calcul
du challenge interclasses.

La colonne Sexe de l’élève est la référence, y compris si le nom de sa classe
contient « filles » ou « garçons ». Un sexe absent ou non reconnu reste dans
une catégorie explicite « sexe non renseigné » ; il faut corriger la liste
avant la course. Les tables, filtres, PDF, feuilles Excel et visuels sociaux
utilisent tous la même catégorisation. Les courses archivées en bénéficient
également lors de l’export Excel, sans migration des données.

La suite de fiabilité comporte maintenant 34 contrôles, dont les rangs CP
filles/garçons avec arrivées mélangées et sexes inconnus, les feuilles Excel
par catégorie et les niveaux CP/CE2/4e/3e/seconde/première/terminale.

## Conclusion

La mise à jour consolide les classements par niveau, la continuité des scans,
les corrections concurrentes et la sauvegarde. Elle ajoute une vue d’ensemble
guidée aux outils existants de dossards personnalisés et de challenge.
Les tests décrits ci-dessous ont réussi. Cela ne constitue pas une garantie
d’absence de bugs, ni une validation de chaque imprimante, douchette ou iPad.

Périmètre : interface Next.js, import Excel/CSV, numérotation, modèles,
prévisualisation et PDF, stockage local, sauvegarde/restauration, programme
des courses, API d’organisation et d’arrivée, fonctions SQL, classements,
challenge et exports. L’audit précédent du 30 septembre a servi de base.

## Règles fonctionnelles conservées

### Une arrivée commune, plusieurs classements

CM1 A, CM1 B, CM1B et CM1 se regroupent en CM1. CM2 A et CM2 B se
regroupent en CM2, séparément. Il en va de même pour les classes de 6e,
5e et les autres niveaux reconnus. Une course peut contenir tous ces élèves
et recevoir leurs scans mélangés. Le rang commun conserve l’ordre d’arrivée ;
chaque classement de niveau reprend à 1. Absents, dispensés et abandons
n’obtiennent pas de rang individuel.

Un libellé CM1/CM2 ne permet pas de savoir le niveau de chaque enfant :
il reste une catégorie distincte. Il faut renseigner un libellé univoque pour
chaque élève avant le départ. Les groupes sans niveau reconnu restent distincts
et font l’objet d’un avertissement lors de la préparation.

### Challenge interclasses

Tous les élèves de la classe comptent. Un arrivé rapporte son rang commun
d’arrivée. Absents et dispensés : dernier arrivé + 1. Abandons : dernier
arrivé + 10. Le total le plus faible gagne. Le classement par niveau ne
change pas cette règle. Le classeur général additionne les points des courses
terminées incluses dans l’export, et conserve les détails de chaque course.

### Plusieurs postes

Jusqu’à quatre postes sont pris en charge. Le poste A scanne le début de la
file, B son tronçon suivant, puis C et D. La fusion est A → B → C → D,
indépendamment de la vitesse de saisie de chaque poste. Il ne faut pas répartir
les élèves aléatoirement entre les postes. Le temps affiché est le délai entre
le départ et le scan serveur, pas la mesure d’un capteur de chronométrage.

### Dossards et sauvegarde

Fonds PNG/JPEG personnalisés, textes et éléments déplaçables, Code 128 et QR,
polices incorporées, deux A5 paysage par feuille A4. Les gardes-fous bloquent
les doublons de numéros, les codes invalides, trop petits, trop fins,
superposés ou hors page. Ils ne remplacent pas un essai d’impression réel.

La sauvegarde v2 inclut les données locales, la clé organisateur et une archive
des courses récupérées du serveur. Si le serveur ne peut pas tout fournir,
l’application demande explicitement si une sauvegarde partielle est souhaitée.
L’archive restaurée peut être exportée en Excel et reste en lecture seule : elle
ne réinjecte pas automatiquement les arrivées dans une course en ligne.

## Tests réalisés

- Tests existants : règles du challenge, rangs par niveau, import Excel/CSV,
  normalisation douchette, fonds PNG/JPEG et PDF de 10, 100, 800 et
  1 500 participants (750 feuilles A4 pour le dernier cas).
- 25 contrôles de fiabilité supplémentaires : variantes de niveaux,
  classements entrelacés, file persistante/FIFO, quota de stockage, file
  corrompue, erreurs temporaires, sauvegardes v1/v2 et fichiers invalides,
  doublons numériques, superpositions, modules et exports de 1 500 arrivées.
- 18 scénarios d’intégration sur le serveur configuré : 1 107 élèves fictifs,
  pagination, double lancement, jonctions concurrentes, limite de quatre
  postes, 120 scans sur quatre postes simultanés, historique propre au poste,
  relance idempotente, doublon interposte, quatre niveaux mélangés, annulation,
  statut/scan et retrait/scan concurrents, suppression pendant la course,
  verrouillage après clôture, correction organisateur, vraie réponse serveur
  archivée et isolation d’un autre accès organisateur.
- TypeScript, ESLint et compilation statique GitHub Pages.
- Les nouvelles fonctions SQL ne sont exécutables ni par `anon` ni par
  `authenticated` ; elles sont réservées au rôle serveur.

Les données de test ont été supprimées dans le périmètre du cross fictif.
Aucun résultat réel n’a été modifié pour ces tests.

## Limites et recette conseillée avant le cross

1. Tester une petite course fictive sur vos PC/iPad, avec vos douchettes.
2. Imprimer quelques dossards à taille réelle, avec votre fond, puis scanner
   les codes au matériel qui sera utilisé le jour J.
3. Vérifier les libellés de classes, le sexe pour les courses filles/garçons
   et les effectifs de chaque course préparée.
4. Vérifier la connexion réseau de chaque poste. Aucun nouveau scan n’est
   accepté hors connexion ; les demandes déjà ajoutées sont conservées et
   reprises au retour du réseau. L’application n’est pas une PWA entièrement
   hors ligne. Le mode privé ou l’effacement du navigateur peut perdre les
   données locales.
5. Ne clôturer qu’une fois les files de tous les postes confirmées. Si une
   course est close avec une file locale non confirmée, le poste affiche les
   numéros à transmettre à l’organisateur, sans les intégrer silencieusement.
6. Télécharger une sauvegarde après clôture. Elle contient les noms d’élèves
   et une clé donnant l’accès organisateur : la conserver de façon confidentielle.
   Le code de poste d’arrivée doit être partagé uniquement avec les personnes
   qui gèrent cette arrivée.

L’aviseur de sécurité du serveur signale une information « RLS enabled, no
policy » pour `cross_stations`. Cette table est volontairement fermée aux
accès directs du navigateur et utilisée par l’API serveur. Ce signal n’est
pas une ouverture des données ; il doit rester surveillé si le modèle
d’authentification évolue.

## Rejouer les contrôles

```bash
pnpm exec tsc --noEmit
pnpm run lint
node --import tsx scripts/race-tests.mts
node --import tsx scripts/acceptance-tests.mts
node --import tsx scripts/reliability-tests.mts
GITHUB_PAGES=true pnpm run build:github
```

Le script `scripts/live-race-tests.mts --live` crée et supprime un cross
fictif sur le serveur configuré. Il nécessite une exécution explicite, jamais
la CI habituelle. Les nouvelles vérifications locales font partie des
contrôles automatiques GitHub.
